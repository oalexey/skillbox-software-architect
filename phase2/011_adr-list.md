## 11. Список ADR

Статус: Предложено.

| ADR | Решение | Обоснование |
|---|---|---|
| ADR-001 | Использовать событийно-доменную архитектуру с выделением критичных масштабируемых сервисов | Поддерживает рост, автономность команд и пиковые нагрузки |
| ADR-002 | Единый identity-слой на базе OAuth 2.0 / OIDC и интеграция с существующими корпоративными приложениями | Упрощает пользовательский путь и продажи |
| ADR-003 | Согласия и приватность как отдельный сервис, версионируемые согласия, принуждение на уровне доступа | Критично для юридических рисков |
| ADR-004 | Offline-first клиент с локальным хранилищем и очередью операций | Тренировки не должны теряться |
| ADR-005 | Activity-домен проектировать как источник событий с идемпотентной записью | Исключает дубли и потерю тренировок |
| ADR-006 | Для метрик тренировки использовать временные ряды, а не только реляционную БД | Эффективность хранения и запросов |
| ADR-007 | Глобальные справочники могут быть централизованы, персональные данные — регионально | Баланс удобства и локализации |
| ADR-008 | Событийная шина как основной механизм интеграции между доменами | Снижает связанность |
| ADR-009 | Уведомления только через единый Notification Hub с предпочтениями и квотами | Борьба со спамом и лучшее управление |
| ADR-010 | Рекомендации строить как комбинацию правил и ML | Правила обеспечивают безопасность и контролируемость |
| ADR-011 | Поиск людей рядом реализовывать через геофаззинг и ограниченные временные окна | Снижение риска приватности |
| ADR-012 | Геймификация и соревнования используют идемпотентные события и антифрод-проверки | Честность результатов |
| ADR-013 | Наблюдаемость через единый стандарт трейсов/метрик/логов | Без этого невозможна эксплуатация |
| ADR-014 | Критичные компоненты проектировать переносимыми между облаками | Снижение стратегического риска |
